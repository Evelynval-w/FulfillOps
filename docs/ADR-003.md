# ADR-003: Worker reliability and observability

- **Status:** Proposed
- **Date:** 2026-11-11
- **Owner:** Saad (reviewed by Makuo and Tony through a pull request)
- **Scope:** How the worker survives crashes, retries and poison jobs, and how we measure it (metrics, logs, SLO).

## 1. Context

Orders are accepted by the API and finished later by a worker (ADR-001, D3 and D4). Any process can be
killed at any moment, and an accepted order must never be lost or completed twice. This record covers
the worker's side of that promise and the numbers we use to see it working. It builds on ADR-001
(rules I4, I5, I7 and decisions D4, D7). Requirements: worker with retries and dead letter, crash
recovery with two workers, `/metrics`, an SLO with a p95 measurement, and an incident postmortem.

## 2. Decisions

### D1. At-least-once delivery, made exactly-once by a fenced completion
- **Chosen:** A job can be delivered more than once (for example after a worker crash). Completing or
  failing a job is a single guarded `UPDATE` that only works if `state = 'claimed'`,
  `locked_by = <this worker>` and `attempts = <the attempt this worker claimed>`. The job update and the
  order update run in one transaction. If the guard matches no row, the worker discards its result.
- **Why:** A worker that is slow or paused can lose its lease while still running. Without the guard it
  could overwrite the result of the worker that took over. Checking `attempts` as well as `locked_by`
  also protects against the same worker id reclaiming its own job.
- **Alternative:** A distributed lock or a "processed" table. Both add a second place to keep consistent,
  and the guarded update already gives the same result in one statement.
- **Requirement:** ADR-001 rule I4; the "completes once" part of the crash gate.
- **Evidence:** `tests/test_worker.py` (`test_a_worker_that_lost_its_lease_cannot_complete`,
  `test_old_attempt_of_the_same_worker_id_cannot_complete`) and the kill-drill log.

### D2. Crash recovery: leases, and a reaper for jobs that run out of attempts
- **Chosen:** A claim sets a 10 s lease. Any worker may claim a job whose lease has expired. A job
  whose lease expires on its last attempt is marked `dead` and its order `failed` by the next worker
  loop. A job with all attempts used is never claimed again.
- **Why:** Without the reaper, a worker that dies on every attempt would leave the job `claimed`
  forever and the order stuck in `processing`. The poison-job gate forbids an infinite loop.
- **Alternative:** A separate janitor process or cron job. It is one more thing to deploy and monitor.
- **Requirement:** Worker crash gate; ADR-001 rules I5 and I7.
- **Evidence:** `test_job_is_reclaimed_after_the_lease_expires_and_completes_once`,
  `test_worker_that_dies_on_every_attempt_ends_failed_not_looping`,
  `tests/test_integration.py` (kill -9 mid-job, job shows 2 attempts).

### D3. Retry policy, as in ADR-001 D7, with the database clock
- **Chosen:** 5 attempts. The wait after attempt n is `2 * 2^(n-1)` seconds (2, 4, 8, 16), plus or
  minus 25 % jitter, capped at 30 s. All times (`lease_expires_at`, `next_run_at`) use the database's
  `now()`, not the worker's clock. A retried order goes back to `queued`.
- **Why:** Two workers (or two pods on different nodes) can disagree about the time. One clock removes
  a class of bugs where a lease looks expired to one worker but not to another.
- **Alternative:** Worker-side timestamps. Simpler to write, but wrong under clock drift.
- **Requirement:** Retries with backoff; poison job reaches `failed` in about 30 s.
- **Evidence:** `test_backoff_is_2_4_8_16_with_jitter_and_cap`, poison drill log (attempts 1 to 5).

### D4. A poison job is simulated with an environment variable, and is off in production
- **Chosen:** `POISON_CUSTOMER_ID` makes the worker always fail orders from that customer. The worker
  ignores the variable when `APP_ENV=production`. There is no special API route.
- **Why:** The drill needs a job that always fails without adding a way to break orders in a real
  deployment. The API contract has no route for it.
- **Alternative:** A hidden API endpoint or a special SKU. Both would exist in the production image.
- **Requirement:** Poison-job gate; security (no test back door in production).
- **Evidence:** `test_poison_customer_is_ignored_in_production`, poison drill log.

### D5. A failed order keeps its stock reserved
- **Chosen:** After the last attempt the job is `dead`, the order is `failed`, `last_error` is saved,
  and the stock is not given back.
- **Why:** The brief forbids automatic restock. The worker cannot know whether a real side effect
  happened before the failure, so releasing stock could oversell.
- **Alternative:** Automatic compensation (restock). Rejected by the brief.
- **Requirement:** ADR-001 rule I7.
- **Evidence:** `test_poison_job_retries_then_fails_without_restock`.

### D6. Metrics for orders and retries come from the database, not from the worker process
- **Chosen:** The API's `/metrics` computes `fulfillops_orders_created_total`,
  `fulfillops_orders_failed_total` and `fulfillops_worker_retries_total` from Postgres at scrape time.
  Retries are `sum(attempts - 1)` over jobs. The worker has no HTTP port and no metrics endpoint.
  `fulfillops_http_requests_total` and the latency histogram are measured inside each API process.
- **Why:** The drill kills workers. Counters kept in a worker would reset to zero on every restart, and
  the contract wants all four series on the API's `/metrics`. Counts in the database survive restarts
  and are the same for both workers.
- **Alternative:** Each worker exposes its own `/metrics` (the usual Prometheus pattern). It needs extra
  ports and scrape configuration and loses its counters at restart. We can add it later for extras
  such as processing time.
- **Requirement:** Contract (four metric series); observability and incident evidence.
- **Evidence:** `/metrics` output before, during and after the kill drill (to be captured).
- **How to read the numbers:**
  - The three database counters are identical on both API replicas, so use `max`, never `sum`.
  - `http_requests_total` and the histogram are per process and reset on restart, so use `sum` with `rate()`.
  - `worker_retries_total` also counts a recovery after a crash (a crash shows as attempt 2), so it
    is evidence for the kill drill as well as for failing jobs.

### D7. Service level objectives (SLOs) and how we measure them
- **Chosen (proposed targets, to be confirmed by our own measurement):**
  1. **Success:** 99.5 % of HTTP requests answered without a 5xx error, over the evaluation window.
  2. **Speed:** p95 of `POST /api/v1/orders` under 300 ms in an isolated local test (the example the brief gives).
  3. **Completion:** 99 % of accepted orders reach `completed` within 15 s of the `202` (the limit the public checker uses), while the workers are not overloaded.
- **How we calculate them:**
  - Success: `1 - sum(rate(fulfillops_http_requests_total{status=~"5.."}[5m])) / sum(rate(fulfillops_http_requests_total[5m]))`, or the same ratio from two `/metrics` readings (before and after) without Prometheus.
  - Speed: `scripts/measure_p95.py` takes 200 sequential samples per endpoint, sorts them and reports the exact nearest-rank 95th percentile. It also estimates p95 from the server histogram (the way `histogram_quantile` does) as a cross-check. The server figure is coarse because it is limited by the bucket edges (0.005, 0.01, 0.025 ... s) and leaves out network and client time.
  - Completion: the same script sends 20 orders, one every 0.5 s, polls each one and records the time until `completed`. It waits for the queue to drain first, so the number does not include a backlog from the earlier phases.
- **Why:** These are the promises a client sees: the service answers, it answers quickly, and the order is finished soon. The 300 ms and 99.5 % figures are the brief's own example targets.
- **Alternative:** Estimate p95 only from histogram buckets. It is coarse for small samples, so we report the exact sample percentile and use the histogram only as a cross-check.
- **Requirement:** Observability and SLO with its limits; at least 200 local samples for a reproducible p95.
- **Evidence:** The JSON summary and the raw-sample CSV that the script writes to `docs/evidence/` (to be added after the run on our own stack). Do not quote any number here until that run exists.
- **Limits of the measurement:**
  - Everything runs on one machine, so the client, API, workers and database share CPU and memory.
  - One sequential client: it shows the cost of a request, not how latency grows under concurrent load or when the queue builds up.
  - Order creation needs stock. The seed has only 24 units, so on the isolated test database we raise `PART-200` stock first. A real shop would not behave like this.
  - The worker's processing time is simulated (0.5 s by default), so the completion time shows our queue and polling behaviour, not a real fulfilment system.
  - The data volume is tiny, so query times are better than production would be.
  - The SLOs do not cover orders that end `failed` on purpose (poison jobs). Those are counted in `fulfillops_orders_failed_total` and discussed in the postmortem.

### D8. Structured logs with the order and job ids, never customer data
- **Chosen:** The worker logs one line per event with `worker`, `order`, `job`, `attempt` and the
  outcome (`claimed`, `failed -> retry in 4.6s`, `completed`, `lease lost`, `dead`). It never logs the
  database URL or customer ids.
- **Why:** The incident postmortem needs a timeline. These lines show who held a job, when, and what
  happened next.
- **Alternative:** A log shipping stack. Too much for the time we have; `kubectl logs` is enough.
- **Requirement:** Observability; security (no secrets in logs).
- **Evidence:** Drill logs (to be saved under `docs/evidence/`).

## 3. Alternatives considered

| Area | Alternative | Why we did not choose it | When it would be the better choice |
|------|-------------|--------------------------|------------------------------------|
| Metrics source | A `/metrics` port on each worker | Counters reset when the pod we kill restarts, and it needs extra ports and scrape config | Per-process detail such as processing time, or a long-running metrics system with `rate()` |
| Crash detection | A janitor process or cron job | One more deployment, and the claim query can already do it | Many queues or very large tables where scanning in the worker is costly |
| Exactly once | Distributed lock or "processed ids" table | A second source of truth to keep in step | Side effects outside the database that must be deduplicated by key |
| Time | Worker clocks | Clock drift between pods | One machine, or a clock that is guaranteed to be synchronised |
| Poison job | Hidden API route or special SKU | It would exist in production | A separate test-only service |

## 4. Consequences

- Killing a worker is safe at any moment: the job is picked up again after at most the lease time
  (10 s), plus the polling interval.
- A crash looks like a retry in the metrics, so `worker_retries_total` is not only "failed attempts".
- Recovery time is bounded below by the lease length. Shorter leases recover faster but take over
  slow jobs more often (see limitations).
- All reliability state is in Postgres, so a database outage stops processing but loses nothing.

## 5. Limitations

| Limitation | Why it exists now | Why it should change | Better solution |
|------------|-------------------|----------------------|-----------------|
| The lease is fixed at 10 s with no renewal | The simulated work is short | A long job is taken over while still running, which wastes work (the fenced completion still prevents a second result) | A heartbeat that extends the lease while the worker is alive |
| Workers poll the table every 0.5 s | No broker (ADR-001 D4) | Constant database load that grows with the number of workers | `LISTEN/NOTIFY`, or a broker for high load |
| Nothing alerts when a job goes `dead` | We only have raw `/metrics` | An operator learns about failed orders only by looking | An alert on `fulfillops_orders_failed_total` increasing |
| A failed order stays failed until a person acts | No automatic restock (D5) | Stock is locked and no one is told | An admin action with an audit log to retry or release |
| Totals come from table scans at every scrape | Small data | `count(*)` over `orders` and `jobs` slows down as the tables grow | Counters in a small summary table, or an incremental counter updated by the worker |
| The simulated work never calls an external system | There is no real fulfilment service | Real side effects would be repeated by at-least-once delivery | Pass the order id as an idempotency key to every external call |
| The SLO is measured on one machine | Time and hardware | It is not a real production claim | Load test on the real cluster with realistic traffic |
